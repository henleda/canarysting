# CanaryPlatform Development Plan

This is the source of truth for CanaryPlatform development sequence, current work, dependencies, validation, blockers, and completion evidence. M1A through M1D retain their historical CanarySting IDs. Allowed status values are `TODO`, `IN_PROGRESS`, `BLOCKED`, and `DONE`. Normally only one task is `IN_PROGRESS`. A task is `DONE` only after every acceptance criterion and its declared validation tier pass; partial code is not completion.

Validation tiers:

- **Tier A — Local:** documentation, pure Go, static analysis, generated code, serialization, and non-kernel refactoring. Typical gates are formatting, vet, focused/race tests, build, generated drift checks, and frontend lint/build when relevant.
- **Tier B — Local plus DGX integration:** eBPF, socket cookies, cgroups, kernel enforcement, Cilium, ARM64, Envoy-to-kernel attribution, DGX scripts, and low-level networking. Tier A plus the relevant DGX proof and cleanup are required.
- **Tier C — Local plus DGX Kubernetes end-to-end:** identity, Kubernetes ingestion/operator/manifests/CRDs, reconciliation, workload scope, policy ingestion, Kubernetes graph construction, and complete request-to-verdict/enforcement behavior. Tier A, relevant Tier B primitives, and DGX K3s end-to-end validation are required.
- **Tier D — DGX attacker/correlation:** CanaryAttacker scenarios, Ollama/Qwen, emitted ground truth, cross-source correlation, and correlation-quality claims. Tier A and relevant Tier B/C primitives plus before/scenario/observe/correlate/cleanup/after evidence are required.

The skill records one product area (`CanaryView`, `CanarySting`, `CanaryAttacker`, `Shared platform`, or `Development infrastructure`) and one equivalent validation label (`local`, `DGX integration`, `DGX Kubernetes end-to-end`, or `DGX attacker/correlation`) before implementation. Historical Tier A/B/C labels remain valid completion evidence.
